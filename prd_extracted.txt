1. Executive Summary
Urban authorities rely on many disconnected sources of information — weather forecasts, satellite imagery, GIS maps, sensors, and field inspections — to manage flood-prone infrastructure. These sources describe conditions, but none of them tell a resource-constrained authority where to send its limited inspection and maintenance teams first.
ORACLE Edge is a cloud-based infrastructure decision-intelligence platform with an IoT edge device. It fuses satellite imagery, weather data, GIS infrastructure information, and real-time sensor measurements to calculate infrastructure risk, prioritize assets by hazard and human impact, and recommend the most appropriate intervention. The platform is demonstrated end-to-end through a physical flood-infrastructure prototype connected to a cloud AI backend.
Core distinction
ORACLE Edge is not another flood-prediction system. It is a decision-support and action-prioritization system: prediction is an input, not the product.
2. Problem Statement
During a major rainfall event, a municipality may be responsible for 100 roads, 30 bridges, 200 drains, and 20 flood-prone zones — while having only a handful of inspection teams, maintenance vehicles, and hours available. Multiple locations can show warning signs simultaneously, and existing tools report rainfall intensity, water levels, flooding, and vulnerable assets individually, but final prioritization is still left to human interpretation under time pressure.
Problem statement
How can heterogeneous environmental and infrastructure data be converted into an explainable, spatially prioritized action plan when government resources are limited?
3. Goals & Objectives
3.1 Product Goals
Fuse satellite, weather, GIS, and IoT sensor data into a single infrastructure risk signal.
Rank vulnerable infrastructure assets by urgency using an explainable ML model.
Translate risk into a concrete, actionable recommendation (monitor, inspect, intervene) rather than a raw score.
Demonstrate a complete physical-to-digital decision loop within a 12-week academic timeline.
3.2 Non-Goals (Out of Scope for this Prototype)
Full city-wide deployment or 100+ physical sensors.
Real integration with government emergency-dispatch systems.
A full digital twin of an entire city, or autonomous traffic control.
Custom satellite models trained from scratch, or drone-based data collection.

6. Data Requirements
The MVP is built on five core data categories, deliberately scoped to avoid data-collection sprawl.
6.1 Satellite Imagery — Sentinel-2 (primary)
Sentinel-2 Level-2A Surface Reflectance provides multispectral imagery for water and land-cover observation, with a 5-day revisit interval via Earth Engine's harmonized collections. Used for water extent, land-cover context, NDWI, and change detection.
NDWI formulation: NDWI = (Green − NIR) / (Green + NIR), producing a water probability / water mask.
6.2 Satellite Imagery — Sentinel-1 (enhancement, optional)
Sentinel-1 SAR data can be acquired regardless of cloud cover, complementing optical Sentinel-2 imagery. For the first prototype, Sentinel-2 + NDWI is sufficient; Sentinel-1 is added as an enhancement, not a dependency.
6.3 Weather / Rainfall
Primary: Open-Meteo — historical and forecast precipitation, temperature, humidity, and wind, sourced from ERA5/ERA5-Land and higher-resolution model products.
Secondary / research layer: NASA GPM IMERG — near-real-time global precipitation at 30-minute temporal and ~0.1° spatial resolution.
Required derived variables: rainfall_last_1h, rainfall_last_3h, rainfall_last_24h, forecast_rainfall.
6.4 GIS / Infrastructure
Source: OpenStreetMap, queried via the Overpass API for tagged map objects. Extracted feature types: roads, bridges, hospitals, schools, buildings, waterways, railways.
6.5 Elevation
Source: NASA SRTM DEM (~30 m resolution, via Google Earth Engine). Used to derive elevation, slope, and drainage/terrain vulnerability context.
7. Machine Learning Requirements
ORACLE Edge separates two distinct ML problems rather than training one large model for everything.
7.1 Problem A — Satellite Water / Flood Detection
Baseline (MVP): NDWI thresholding — a working water-detection module with no training required.
Advanced (Phase 2): Sen1Floods11 — a georeferenced Sentinel-1 flood dataset for training/testing a U-Net or lightweight segmentation model to produce a flood / non-flood mask.

7.3 Algorithm Selection
Recommended: XGBoost / LightGBM — strong performance on tabular data, fast, explainable, easy to deploy, and effective with mixed numerical features and modest dataset sizes. Logistic Regression and Random Forest should be trained as comparison baselines to support a proper model-selection evaluation.
7.4 Training Data Strategy
Labelled Indian infrastructure-failure data at scale is unlikely to be available, so training uses a hybrid strategy combining historical/public event data, satellite-derived features, weather history, and expert-designed synthetic sensor scenarios (e.g., low rainfall + stable water → Low Risk; extreme rainfall + flooding + hospital dependency → Critical Risk). This limitation must be stated explicitly in the final report as an academically honest scoping decision — field deployment would require calibrated municipal sensor data.
8. Risk & Priority Scoring Model
8.1 Component Scores
Score
Composed Of
Hazard (H)
rainfall + water_level + water_rise_rate + satellite_water_change + terrain
Exposure (E)
population + roads + buildings + critical_facilities
Vulnerability (V)
asset_criticality + historical_failure + terrain
RISK = f(H, E, V), learned by the ML model rather than hard-coded, so the scoring logic remains explainable while still being data-driven.
8.2 Priority Score
The highest-hazard location is not automatically priority #1 — consequence of failure matters. Example: Location A (flood risk 95, population impact 20, no hospital dependency) may be ranked below Location B (flood risk 82, population impact 90, hospital dependency 100), because B's failure carries greater human consequence.
8.3 Explainability
Each risk score must be decomposable into contributing-factor weights (e.g., via SHAP), surfaced to the user as a "Why this risk?" breakdown rather than an opaque number.

9.2 Asset-Type Rules
Bridge + critical risk → Dispatch inspection team.
Drain + critical risk → Dispatch maintenance team.
Road + critical risk → Recommend traffic diversion.
School + severe flood exposure → Issue emergency warning.
9.3 Resource Allocation
Given a fixed number of available teams, the Action Engine assigns them against ranked priorities — e.g., with 3 teams available and priorities Bridge B17, Drain D03, Road R08 ranked #1–#3, ORACLE assigns Team A → B17, Team B → D03, Team C → R08. This moves the system from prediction toward an operational decision-support product.

10.4 Edge-to-Cloud Transport
MQTT is preferred for architectural fidelity to a real IoT deployment (ESP32 → MQTT Broker → FastAPI ingestion service → PostgreSQL). If MQTT adds excessive early complexity, the team should start with HTTPS/REST and migrate to MQTT once the pipeline is stable.
11. System & Cloud Architecture
Internet → API Gateway → FastAPI application layer, ingesting sensor, weather, and satellite data in parallel into a common data pipeline, backed by PostgreSQL + PostGIS. A feature pipeline feeds the ML inference service, which produces a risk score and explanation; these feed the Priority Engine and then the Action Engine, which drives both the Dashboard and the Alert Service.
11.1 MLOps Pipeline
Data Collection → Data Validation → Feature Engineering → Model Training → Model Evaluation → Model Registry → Containerization → Cloud Deployment → Inference API → Monitoring.

Positioning
